# 法律文档智能检索引擎（Legal RAG Search）— 毕业设计答辩报告

> 基于 BM25 + 向量语义混合检索与 DeepSeek 大模型的 法律 RAG 智能问答系统
> 技术栈：C++17 / Qt / CMake / cppjieba / DeepSeek API

---

## 一、选题背景与意义

### 1.1 背景

裁判文书等法律文档数量庞大且增长迅速，法律从业者与普通民众在检索法律文书时面临三个痛点：

1. **检索门槛高**：法律文书使用规范术语（如"职务侵占罪"），而用户提问往往是口语（如"公司把钱吞了"），传统关键词检索难以跨越这一词汇鸿沟；
2. **通用搜索引擎不"懂"法律**：无法按案号、法院、案件类型、审判程序等结构化信息过滤，也无法理解"这些案件一共有多少起"这类跨文档汇总问题；
3. **只给链接不给答案**：用户需要自行阅读多份长文书归纳结论，阅读成本高。

### 1.2 意义

本设计实现一个**面向法律文书的 RAG（Retrieval-Augmented Generation，检索增强生成）桌面搜索引擎**：

- 检索层针对法律语料定制：法律术语分词词典 + 文书元数据（案号/法院/日期/案件类型）自动提取 + 多维筛选；
- 生成层接入大模型（DeepSeek），将检索到的文书片段作为上下文，按法律问答模板生成**带引用来源、结构化、附免责声明**的回答；
- 全部核心模块（PDF 解析、倒排索引、BM25、混合融合、流式生成）**自行实现，零重型外部依赖**，适合桌面端离线部署。

### 1.3 RAG 相对纯大模型问答的优势

| 维度 | 纯大模型 | RAG（本系统） |
|---|---|---|
| 事实依据 | 依赖训练记忆，易编造（幻觉） | 回答必须基于检索到的真实文书，可溯源 |
| 时效性 | 训练截止后失效 | 语料随时导入更新 |
| 私有语料 | 无法访问 | 本地文档即插即用 |
| 可解释性 | 黑盒 | 每个回答附带【来源 N】引用与相关度得分 |

### 2.2 技术选型与理由

| 选型 | 决策 | 理由 |
|---|---|---|
| 开发语言 | **C++17**（而非 Python） | 桌面原生性能；倒排索引/分词/排序等核心算法手写实现，教学与答辩价值高；内存占用小 |
| UI 框架 | **Qt Widgets（Qt 5/6 双版本兼容）** | 成熟跨平台桌面方案；`QNetworkAccessManager` 原生支持 HTTP/SSE；CMake 自动探测 Qt6 回退 Qt5，代码经双版本 API 审查（条件编译隔离弃用属性） |
| 中文分词 | **cppjieba + 自定义法律词典** | MIT 协议可分发；支持用户词典注入，解决"知识产权法院"等复合法律术语被切散的问题 |
| 排序算法 | **Okapi BM25（k1=1.5, b=0.75）** | 词频饱和 + 文档长度归一化，短查询场景表现稳健，无需训练 |
| 语义检索 | **Embedding API + 余弦相似度**（预留接口） | 与 BM25 加权融合（0.4/0.6）；服务不可用时自动降级 |
| 大模型 | **DeepSeek Chat（SSE 流式）** | OpenAI 兼容协议、成本低、中文法律语料表现好；流式输出保证交互体验 |
| 构建 | **CMake + MinGW/MSVC 双支持** | 跨编译器可移植（本设计在 GCC 8.1 与 GCC 13 两代工具链上均验证通过） |

## 三、系统架构与端到端流程

### 3.1 架构总览

```
┌──────────────────────────────────────────────────────────┐
│                      Qt 桌面 UI（主窗口）                  │
│   搜索栏 ｜ API Key 配置 ｜ 类型/法院/年份筛选 ｜ 结果列表+AI回答双栏 │
└───────────────────────────┬──────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────┐
│                 RAG 混合检索器（Retriever）                │
│   ┌────────────────┐      ┌───────────────────────┐      │
│   │ BM25 排序器     │      │ 向量相似度引擎(余弦)    │      │
│   │ k1=1.5,b=0.75  │      │ (Embedding API 预留)   │      │
│   └───────┬────────┘      └───────────┬───────────┘      │
│           │                           │                  │
│   ┌───────▼────────┐      ┌───────────▼───────────┐      │
│   │ 倒排索引        │      │ Embedding Service      │      │
│   │ (chunk 级)     │      │ (API 不可用自动降级)    │      │
│   └────────────────┘      └───────────────────────┘      │
│                                                           │
│   文档解析(PDF/TXT) → 文本分块 → 分词 → 建索引 → 元数据提取   │
└───────────────────────────┬──────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────┐
│                AI 生成器（Generator）                      │
│   法律/通用双 Prompt 模板 ｜ SSE 流式解析 ｜ DeepSeek Chat   │
└──────────────────────────────────────────────────────────┘
```

### 3.2 端到端数据流

**离线（文档导入）**：`📂 导入文档` → 格式路由（PDF 走自研解析器提取文本层 → 为空则 OCR 级联回退）→ UTF-8 安全分块（512 字节/50 字节重叠）→ cppjieba + 法律词典分词 → 写入倒排索引与块存储 → 全文元数据提取（案号/法院/日期/类型/当事人/程序）。

**在线（检索问答）**：输入问题 → 分词（+位置问句扩展）→ BM25 与向量双路召回 → 最大值归一化加权融合（0.4/0.6）→ 聚合/聚焦双模式路由 → 客户端三维筛选 → 拼接【来源 N】上下文 → 法律/通用 Prompt 模板 → DeepSeek SSE 流式生成 → 逐字上屏 + 结果列表展示得分。

### 3.3 关键设计决策

**① 分块：512 字节 + 50 字节重叠，UTF-8 边界安全**
按字节切分保证中英文一致的块大小预算；切分前回退到合法 UTF-8 边界（避免切断多字节汉字），再在预算后半段向前寻找自然断点（`\n` `.` `!` `?`）；重叠防止语义被截断。512 字节约合 170 个汉字，兼顾召回精度与上下文预算。

**② 法律自定义词典**
在 cppjieba 标准词典之上注入约 350 条法律术语（诉讼程序/法院机关/刑法/合同法/公司法/知识产权/劳动法等 10 类），保证「知识产权法院」「附带民事诉讼」等复合术语不被切散——这是法律领域 NLP 区别于通用搜索的关键定制点。

**③ 聚合/聚焦双模式路由**
对「这些案件/所有案件/汇总/一共」等明确聚合意图的短语做子串匹配触发聚合模式：扩大召回（topK=50）、每文档最多保留 2 块以保证文档多样性、并向生成器注入**全部文档的元数据汇总**，使"总共有多少起案件"这类跨文档统计问题可答；其余问题走聚焦模式保持原始排序。

**④ 优雅降级**
Embedding/LLM 均为外部服务。任一服务不可用时系统不崩溃：向量路失效自动退化为纯 BM25；未配置 Key 时 AI 面板给出明确引导，检索/筛选/元数据功能完整可用。此设计保证离线演示与低配环境可用性。

**⑤ 法律 Prompt 模板**
自动检测上下文是否为法律文书（案号/法院/原被告等标记），切换四段式法律问答模板：案件概述 → 法律分析 → 结论 → 参考来源；系统提示词强制要求引用案号并附「本回答仅供参考，不构成法律意见」免责声明。

### 4.3 真实文书实测与迭代修复

在 21 篇模拟语料之外，用**两份真实法律文档**做了实战验证：一份真实民事判决书 PDF（文字型，WPS 导出），一份 20 页起诉状扫描件 PDF（15.8 MB，纯图片页）。实测暴露了 5 个真实环境问题，全部定位根因并修复：

| # | 问题 | 根因 | 修复 |
|---|---|---|---|
| 1 | 真实判决书导入失败 | WPS 导出的 PDF 使用 CID 子集字体 + ToUnicode CMap，自研轻量解析器不支持该编码，文本层提取为空后触发 OCR 回退，而 OCR 环境缺失 | 部署 Python + PyMuPDF + RapidOCR；级联第 1 级即完整提取该 PDF（9 页） |
| 2 | 装了 Python 仍报找不到解释器 | Windows 商店占位 `python.exe` 驻留 PATH，遮蔽真实安装 | `findPython` 优先扫描官方标准安装位置（版本号倒序），逐候选实测 `import fitz` |
| 3 | 导入扫描件时程序"未响应"约 3 分钟 | OCR 逐页约 8 秒 × 20 页，`QProcess::waitForFinished` 同步阻塞 UI 线程不派发绘制事件 | 等待改为事件循环（持续泵绘制事件、屏蔽输入防误操作）；超时 5→10 分钟；状态栏提示 OCR 耗时 |
| 4 | AI 生成报「TLS initialization failed」 | 部署时缺少 Qt HTTPS 依赖的 OpenSSL 1.1 动态库（Qt 5.15 不兼容 OpenSSL 3） | 部署 `libssl-1_1-x64.dll`/`libcrypto-1_1-x64.dll`，沉淀部署清单 |
| 5 | AI 回答流式输出完毕后报 `substr: __pos > size` | SSE 解析用 `getline` 计数回退：流末尾以无换行的半行结束时，尾行被补上虚构的 `\n` 计入已消费长度，`substr` 越界 | 重写为标准 SSE 缓冲处理：只消费完整行，尾行留缓冲区，流结束后处理残留行 |

修复后复测：判决书（文字型）与起诉状（扫描件）均可正常导入、检索（OCR 文本命中「工伤认定」「泰源精密」等）、元数据自动提取（年份/法院级别），流式 AI 生成完整输出四段式法律分析并带来源引用，全过程窗口无假死。

> 这轮实测的价值：模拟语料验证"功能正确性"，真实文书验证"工程健壮性"。每一步根因分析均已沉淀至踩坑记录 `TROUBLESHOOTING.md`（#17–#21），并新增回归测试守护核心路径。

## 五、量化实验

### 5.1 实验设置

- 语料：21 篇模拟裁判文书（8 民事/5 刑事/3 行政/3 知产/2 商事，118 文本块）
- 查询集：**23 条人工标注查询**，覆盖案情描述型（11）、法律术语型（7）、易混区分型（3）、多相关文档型（1）、口语改写型（1）
- 指标：Hit@5、Recall@10、MRR（文档级排名：同文档多块取最高名次）

### 5.2 结果

| 指标 | 数值 |
|---|---|
| **Hit@5** | **0.957**（22/23 条查询在 Top-5 命中相关文书） |
| **Recall@10** | **0.957** |
| **MRR** | **0.913**（21/23 条查询相关文书排名第 1） |

易混区分型查询 **3/3 全部正确**（职务侵占 ≠ 损害公司利益；商标行政无效 ≠ 商标民事侵权），验证了法律词典与案由词的判别力。

### 5.3 失败案例分析与改进方向

唯一失败查询「电信诈骗数额较大怎么判刑」暴露了**中文词汇失配**问题：查询用口语「诈骗/数额较大/判刑」，文书用规范表述「诈骗罪/数额特别巨大/判处有期徒刑」，四组词面全部错开导致 BM25 零得分。

这一案例**实证了纯关键词检索的边界**，也正是系统引入向量语义支路的动机：embedding 能将「诈骗」与「诈骗罪」映射至邻近语义空间。改进路线：① 接入 OpenAI 兼容 embedding 服务启用混合检索；② 增加法律用语同义词/归一化层（诈骗→诈骗罪、判刑→判处有期徒刑）。

## 六、不足与展望

| 类别 | 现状 | 展望 |
| --- | --- | --- |
| 向量检索 | 接口与融合框架已就绪，但 embedding 提供方需可配置（当前硬编码指向无 embeddings 服务的端点） | 抽象为可配置 BaseURL/Model，支持智谱/硅基流动/Ollama 本地模型 |
| 排序精调 | 无重排（rerank）阶段 | 引入交叉编码器重排 Top-50 |
| 查询理解 | 聚合路由为短语匹配；无同义词归一化 | 意图分类小模型 + 法律同义词表（可消解第 5.3 节失败案例） |
| 工程化 | UI 层无自动化测试；曾记录一次 GUI 长会话偶发异常（重启后不可复现，已加核心层回归测试守护） | Qt Test UI 自动化；压测定位偶发异常根因 |
| 索引持久化 | 索引驻留内存，重启需重新导入（扫描件需重跑 OCR），对多文档日常使用影响较大；经权衡列入后续迭代 | 落盘文档文本（含 OCR 结果）至本地索引文件，启动时重建内存索引（秒级），无需重复 OCR |
| 评测规模 | 23 条查询 / 21 篇语料（演示级） | 扩充至真实裁判文书开放数据集（如 CAIL），报告置信区间 |

## 七、结语

本设计完整实现了从**文档摄入 → 法律定制化索引 → 混合检索 → 意图路由 → 流式生成**的 RAG 全链路，核心模块全部手工实现并通过 45 项自动化测试与实机端到端验证；量化评测 Hit@5/R@10/MRR = 0.957/0.957/0.913，并通过失败案例的根因分析明确了向量语义检索的工程价值。系统进一步经受了**真实法律文档的实战检验**——文字型判决书与 20 页扫描件起诉状均可完成"导入（含 OCR）→ 检索 → 元数据筛选 → 流式 AI 引用作答"全流程，实测暴露的 5 个工程问题全部根因定位并修复沉淀。系统在无网络、无 API Key 环境下仍保持完整检索能力，具备实际部署与演示价值。
