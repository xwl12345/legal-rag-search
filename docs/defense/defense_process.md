## 二、讲解时间轴（12 分钟标准版）

| 时间 | 环节 | 讲稿要点（说这些，不念稿） |
|---|---|---|
| 0:00–1:00 | **开场：选题与痛点** | 法律文书检索三个痛点：口语与法术语的词汇鸿沟（举例：用户搜"公司把钱吞了"，文书里写的是"职务侵占罪"）；无法按案号/法院/类型过滤；只给链接不给答案。一句话立意：**做一个"懂法律文书"的检索 + 基于真实文书的可信问答系统** |
| 1:00–2:30 | **架构与技术栈** | 一页架构图：UI → 混合检索器（BM25+向量融合）→ 法律定制索引（分块/词典/元数据）→ DeepSeek 流式生成。技术栈一句话：C++17/Qt 手写核心算法，cppjieba+法律词典，DeepSeek API。强调 RAG 价值：回答必须基于检索到的真实文书、可溯源、抑制幻觉 |
| 2:30–5:30 | **三个核心技术点**（各 1 分钟，讲设计动机而非流水账） | ① **UTF-8 安全分块**：512 字节+50 重叠，字节切分保证中英文一致预算、回退 UTF-8 边界防止切断汉字（举被切断的例子）；② **法律词典 + 元数据提取**：350+ 术语词典保证「知识产权法院」不被切散；正则不可靠处手写字节扫描提取案号/法院/日期（含中文数字），实测案号 21/21；③ **聚合/聚焦双模式路由**：识别"这些案件一共有多少起"类跨文档问题，扩大召回+文档去重+注入全库元数据。若时间富余补第 4 点：**优雅降级**——无 Key/断网时检索功能完整可用 |
| 5:30–8:30 | **现场演示** | 见第三节演示脚本（核心 6 步约 3 分钟） |
| 8:30–10:30 | **验证与实验** | ① 45 项自动化测试（解析/分块/BM25/元数据/E2E）全绿；② 量化评测：23 条标注查询，**Hit@5/R@10/MRR = 0.957/0.957/0.913**，易混案由 3/3 区分正确；③ **真实文书实战**：文字型判决书 + 20 页扫描件起诉状全流程跑通，实测暴露 5 个工程问题全部根因修复（举 SSE 越界或 OCR 假死一例讲 30 秒，体现工程素养） |
| 10:30–11:30 | **不足与展望** | 诚实 3 条：索引纯内存（持久化方案已设计）；向量路待接入可用 embedding 服务（失败案例证明必要性）；评测为演示级规模（可扩 CAIL 数据集） |
| 11:30–12:00 | **结语** | 一句收束：完整 RAG 链路 + 45 测试 + 量化指标 + 真实文书实战，具备真实部署价值。致谢 |

### 应急预案

| 意外 | 处置 |
|---|---|
| 断网 / AI 报网络错误 | 检索演示完全本地不受影响，照常；AI 环节切**录像**，口播"回答基于刚才检索到的文书片段" |

## 四、预设评委问题与参考答案（15 问）

**Q1：BM25 和向量的融合权重 0.4/0.6 怎么定的？**
A：经验起点 + 语料实测标定。本语料法律术语密度高，BM25 判别力强，但为给语义路留权重、参考通用实践取 0.4/0.6。评测集上该组合 Hit@5 达 0.957；权重是编译期常量，后续可做成可调参数并用查询集网格搜索。

**Q2：分块 512 是字节还是字符？为什么重叠 50？**
A：512 **字节**（约 170 个汉字），保证中英文统一的块大小预算；切分时回退 UTF-8 边界防止切断汉字，并在预算后半段找自然断点（句号/换行）。50 字节重叠（约 16 字）用于缓解语义截断，实测该设置下 21 篇文书 118 块、评测未出现因切块导致的相关文書漏召。

**Q3：为什么自己写 PDF 解析器而不用 PDFium/Poppler？边界在哪？**
A：轻量零依赖 + 算法实现的教学价值，覆盖 FlateDecode/ASCII85 解压与文本操作符。诚实说明边界：不支持 CID 子集字体 + ToUnicode 映射（真实 WPS 导出文书），实测遇到后由 OCR 级联兜底（PyMuPDF 文本层提取完整成功）。后续增强方向是解析 ToUnicode CMap。

**Q4：向量检索用的什么模型？为什么演示是纯 BM25？**
A：架构上 BM25 与向量加权融合（0.4/0.6），向量路通过 OpenAI 兼容 embeddings 接口接入。当前部署环境未接入可用的 embedding 服务（DeepSeek 不提供该端点），系统按设计**自动降级**为纯 BM25——降级本身是被测试覆盖的一等路径。评测中发现的词汇失配失败案例（"诈骗"vs"诈骗罪"）恰好论证了接入语义检索的必要性，这是明确的迭代方向。

**Q5：为什么用 C++ 不用 Python？**
A：三点——桌面原生性能与低占用；倒排索引/BM25/分块等核心算法手写实现，工程与学习价值高；Qt 成熟桌面方案。代价是迭代效率低于 Python，用"零重型依赖、跨 Qt5/6 可移植"来平衡。

**Q6：和 Elasticsearch、LangChain 等现成方案比，你的价值是什么？**
A：ES 是分布式服务，部署重，本方案是单文件桌面级、离线可用，面向个人法律文书管理场景；LangChain 是编排框架，检索内核仍需自选，本设计自写了从解析到排序的完整内核，可深度定制法律领域逻辑（词典/元数据/双模式路由）。定位差异而非替代。

**Q7：索引为什么在内存？怎么改持久化？**
A：当前规模（百篇级）重建在秒内，持久化优先级后置。方案已设计：把每篇的抽取文本（含 OCR 结果）落盘为本地索引文件，启动时读盘重建倒排索引（分词+建索引为毫秒级），无需重跑 OCR；演示中"重启需重导"就是该不足的活例子。

**Q8：法律词典怎么来的？如何维护？**
A：自建 350+ 条，按诉讼程序/法院机关/刑法/合同法/公司法/知产/劳动法等 10 类整理，cppjieba 用户词典格式加载。更新即编辑词典文件热加载；后续可从文书语料统计新术语半自动扩充。

**Q9：元数据提取准确率怎么验证？**
A：E2E 断言：21 篇文书中案号 21/21、日期 21/21、类型 21/21、法院 19/21（2 篇无"人民法院"字样属预期），含中文数字日期与全角括号等边界。真实起诉状 OCR 文本上同样提取出了年份与法院级别。

**Q10：聚合意图怎么识别？误判怎么办？**
A：对「这些案件/所有/汇总/一共」等明确聚合短语做子串匹配——刻意用窄表避免误伤聚焦型查询。局限是覆盖不全，改进方向是小样本意图分类。误判代价可控：仅影响召回宽度与去重策略，不影响正确性。

**Q11：怎么防止大模型幻觉？**
A：四层——RAG 架构强制回答基于检索片段；Prompt 模板强制「参考来源」章节与案号引用；temperature 0.3 降低发散；界面固定输出「仅供参考，不构成法律意见」免责声明。且每条回答可对照左侧结果列表溯源。

**Q12：23 条查询的评测规模够吗？**
A：作为毕业设计的演示级标注集，方法标准（qrels 人工标注、文档级排名、标准指标），结论可用于定位问题（如词汇失配案例就是评测发现的）。要下统计学结论需扩到 CAIL 等公开数据集千条级，已在展望中。

**Q13：讲一个你印象最深的排查经历？**
A（建议讲 SSE 越界）：AI 回答已完整流式输出却在收尾报 `substr: __pos(1409) > size(1408)`——差一错误。根因是 getline 解析 SSE 时，流末尾无换行的半行被补了虚构的换行计入"已消费长度"。重写为只消费完整行的标准写法，并补了缓冲区残留处理。体会：流式协议解析的记账必须以真实分隔符为界。

**Q14：性能怎么样？**
A：21 篇 / 118 块规模下检索毫秒级；9 条压力查询 E2E 全部通过。导入瓶颈在 OCR（约 8 秒/页），已用响应式等待保证界面不冻结；索引重建与检索均与语料规模线性相关，当前场景无压力。

**Q15：涉密/隐私问题？文书数据会上传吗？**
A：全部本地处理（索引、检索、筛选）；仅调用 DeepSeek API 时会把**检索到的相关片段**随问题发送用于生成回答，这一点通过免责声明与使用场景（公开裁判文书）限定。若用于敏感文书，可将生成端替换为本地部署模型（接口兼容）。

## 五、注意事项

1. **演示纪律**：每次搜索前先念出查询词；每个结果出来先讲"符合预期"再讲机制
2. **时间纪律**：演示超过 4 分钟立即跳到 AI 环节（评委最想看的部分）；被追问时不恋战，"细节在报告 §4.3 有完整记录"
3. **诚实纪律**：向量路未接通、索引未持久化、评测规模小——主动讲透一个短板比被评委挖出来体面得多
4. **设备纪律**：答辩前用答辩现场同款投影/分辨率试一次（高分屏缩放已适配，但需确认投影 DPI 行为）
